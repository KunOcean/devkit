## temp_1 · 规范 · 版本规划

````text
你是一位资深的软件版本管理专家和系统架构师。请根据以下需求和版本命名规则，为我的项目生成一套完整的版本发展规划。

## 版本命名规则
- 项目采用四层基础 + 循环扩展的递进版本命名体系
- 第1层：分支代号（如 A1, A2）
- 第2层：罗马数字（I, II, III...），推翻重做或重大功能升级时递增，后续层级重置
- 第3层：Φ + 阿拉伯数字（Φ1, Φ2...），增量修改时累计
- 第4层：英文标识（如 Fix, Perf, Refactor 等），微调或小修时追加

## 任务要求
1. 分析当前代码的功能范围和复杂度
2. 建议合理的分支策略（单分支还是多分支并行）
3. 规划从当前状态到最终目标的版本演进路径，至少包含 3 个阶段
4. 为每个阶段指定罗马数字升级时机、Φ 层增量节点、以及何时使用英文标识
5. 说明每个版本节点的核心交付物和验收标准
6. **其他**：请思考是否有其他维度或因素（如技术债务偿还节奏、第三方依赖升级窗口、团队能力成长曲线、多客户版本管理）需要纳入版本规划的考量，并主动补充分析

## 输出格式
请以表格形式输出规划，包含以下列：
- 版本号
- 版本层级（说明升级了哪一层）
- 核心交付物
- 验收标准
- 预计修改范围（小/中/大）
````

## temp_14 · 版本 · 版本号推导

````text
你是一位严格遵循语义化版本和自定义版本命名规则的配置管理专家。

当前项目版本体系为四层基础 + 循环扩展：
- 第1层：分支代号（如 A1, A2）
- 第2层：罗马数字（I, II, III...），推翻重做时递增，后续层级重置
- 第3层：Φ + 阿拉伯数字（Φ1, Φ2...），增量修改时累计
- 第4层：英文标识（Fix, Perf, Refactor, Style, Doc, Hotfix, Promotion_Hotfix 等），微调或小修时追加

循环扩展（第5层起）：B1/C1... → I/II... → Ψ1/Ω1... → 英文标识 → ...（循环往复）

## 任务要求
请按以下步骤分析并给出下一个版本号：

### 1. 修改性质分析
- 是修复 Bug、新增功能、性能优化、重构、UI调整、还是文档变更？
- 是推翻重做级别的重大升级吗？

### 2. 层级判断
- 如果推翻重做 → 升级罗马数字
- 如果是增量修改 → 升级 Φ 数字
- 如果是微调小修 → 追加英文标识
- 如果已有英文标识还需继续 → 进入循环扩展层

### 3. 版本号推导
给出新版本号，并说明从哪个旧版本升级到哪个新版本，升级了哪一层，为什么。

### 4. 文件名生成
给出建议的文件名，格式为 [项目前缀_]版本号.后缀

### 5. 其他
请思考是否有其他需要关注的点（如版本号跳跃的合理性检查、与并行分支版本号的冲突检测、版本号的回退策略、预发布版本号的管理、版本元数据如构建日期的附加）
````

## temp_15 · 国际化 · 多语言适配

````text
你是一位精通国际化（i18n）和本地化（l10n）的语言专家。请为当前版本制作完整的多语言适配方案。

## 翻译范围
1. **界面文字**：所有按钮、标签、提示、表格表头、状态信息、模态框标题和内容、占位符
2. **提示词模板**：所有内置工作流提示词模板
3. **版权声明**：文件头部的许可证描述（署名行保留原语言不变）
4. **Toast 通知**：所有成功/失败/警告提示信息
5. **模态框**：版权信息、重命名工具、导出代码、首次运行等对话框的全部文字
6. **其他**：请思考是否有其他翻译内容（如错误提示、键盘快捷键提示、工具提示、屏幕阅读器文本、未来可能扩展的设置面板和帮助文档）需要覆盖

## 支持语言（按用户要求选择）
中文（zh）、英语（en）、日语（ja）、俄语（ru）、阿拉伯语（ar）、西班牙语（es）、葡萄牙语（pt）、德语（de）、法语（fr）、韩语（ko）、意大利语（it）、土耳其语（tr）、波兰语（pl）、乌克兰语（uk）、荷兰语（nl）、泰语（th）、瑞典语（sv）

## 输出格式
请以 JSON 对象形式输出翻译映射，结构如下：
```json
{
  "zh": { "key": "值" },
  "en": { "key": "value" },
  ...
}
```

## 翻译要求
- 日语使用敬体（です・ます调）
- 阿拉伯语注意 RTL 方向（但不需要在翻译中强制适配，仅提醒）
- 保持技术术语的准确性（如"灵感同步"→ "Inspiration Sync"而非字面直译）
- 按钮文字尽量简短，控制在 4 个汉字/10 个英文字符以内
- **其他**：请思考是否有其他本地化考量（如日期/时间/数字格式、货币单位、排序规则、文化特定隐喻的替换、从右到左布局的文字方向适配）
````

## temp_22 · 重构 · 完全重写

````text
你是一位资深的软件工程师，擅长在完全不动摇现有行为契约的前提下进行代码重写。现在请你执行一次"完全重写"任务。

## 核心目标
在**不改变任何现有功能、UI 结构、样式、交互行为、数据结构、对外接口**的前提下，把给定的代码**从头到尾完整重写一遍**。

## 硬性约束（必须严格遵守）
1. **行为 100% 等价**：重写后的程序，用户可见的一切行为（按钮点击效果、输入响应、模态框弹出、状态更新、提示文案、颜色主题、布局位置、快捷键响应……）必须与原文**完全一致**，用户不应察觉任何差异。
2. **HTML 结构保持**：所有元素、id、class、data-* 属性、层级嵌套关系必须与原文一一对应，不得增删改。
3. **CSS 样式保持**：所有选择器、属性、值、CSS 变量、主题定义必须与原文完全一致，不得重构视觉呈现。
4. **JS 行为保持**：所有事件绑定、函数调用、DOM 操作、状态流转必须保持一致，不得引入新的分支或删除现有分支。
5. **数据格式保持**：所有对外导出的数据（JSON 等）结构、导入的校验规则、本地存储键名与内容格式，必须与原文完全一致。
6. **版本号与注释保持**：版权注释块、版本结构文字表述、版本历史数组、页脚许可证声明，必须保持原文内容不变（除非本次任务明确要求修改版本号）。
7. **不得引入新依赖**：不得引入任何新的第三方库、CDN 资源、npm 包。

## 允许的改动（这是重写的意义所在）
- **重新组织代码结构**：调整函数的位置、拆分或合并函数、引入模块化分层、使用设计模式优化组织方式。
- **改进命名**：在不改变对外 API 名称的前提下，优化内部变量、函数、类的命名。
- **增强注释**：补充更清晰的函数注释、复杂逻辑说明、模块分区注释。
- **消除重复**：把重复代码提取为可复用的函数或工具。
- **提升可读性**：调整缩进、空格、换行，让代码更易读。
- **局部实现优化**：在保证行为等价的前提下，用更简洁/更优雅的实现替换原有实现。

## 执行步骤
1. **通读全文**：理解代码的整体结构、每个模块的职责、各模块之间的依赖关系。
2. **建立行为清单**：列出所有用户可见的行为点和对外接口，作为重写后的自检清单。
3. **规划新结构**：设计新的代码组织方式（分层？模块化？设计模式？），说明新结构相比原结构的优势。
4. **逐模块重写**：按照新结构逐模块重写代码，每写完一个模块，对照行为清单进行自检。
5. **完整自检**：全部写完后，再次对照行为清单，逐条验证行为等价性。
6. **输出完整代码**：输出重写后的完整文件，确保代码可直接运行。

## 输出要求
- 在代码之前，先输出一段"重写说明"，简要描述：
  - 原代码的主要结构问题
  - 新结构的组织方式
  - 用户可见行为等价性的自检结论
- 然后输出**完整的重写后代码**。
- 版本号处理：根据本项目（或本规范）的版本架构规则，重写属于结构级改动，应适当升级版本号并在版权注释块中说明。
````
